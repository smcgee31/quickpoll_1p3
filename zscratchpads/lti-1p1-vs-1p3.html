LTI 1.1 versus LTI 1.3

The same poll tool, launched two ways. This page puts the two side by side: the launch, the keys, the message, the checks, the setup, and what each one needs from Canvas.

The short version

📮
LTI 1.1: a signed form
Canvas fills in a web form and signs it with a secret that Canvas and the tool both know. The browser posts the form. The tool signs the same fields again and compares.
🪪
LTI 1.3: a signed token
The tool starts a login. Canvas then sends a token (a JWT) that Canvas signed with its private key. The tool checks it with Canvas's public keys. Nobody shares a secret.
Everything on this page comes from two working apps. QuickPoll 1.1 and QuickPoll 1.3 run side by side in the same local Canvas. The 1.3 facts (roles, claims, ids) come from real launches, checked on 2026-11-14. All names and ids in the samples below are made up. Real launches hold student and teacher data (FERPA, and GDPR for EU users), so keep them out of docs and chat.

The launch, step by step

Both diagrams show a click on the course menu link. Time runs top to bottom. A solid arrow is a request. A dashed arrow is the answer.

LTI 1.1 One trip

LTI 1.3 Two trips and a key download

Why 1.3 adds a login trip. The tool picks the nonce and Canvas puts it inside the signed token. When the token comes back, the tool knows it answers a login it started. In 1.1 Canvas picks everything, so the tool can only check that the form is fresh and new.

Who holds which key

LTI 1.1 One shared secret

🏢Canvas holds the secret. It signs the form.
🛠The tool holds the same secret. It signs the fields again and compares.
⚠If either copy leaks, anyone can forge a launch. A copy sits in two databases.

QuickPoll 1.1 stores it in lti_consumers.shared_secret. A launch names its consumer with oauth_consumer_key.

LTI 1.3 Two key pairs

🏢Canvas signs the launch token with its private key. It publishes the public key at a JWKS URL.
🛠The tool downloads that public key and checks the token. It keeps no Canvas secret.
🔑The tool has its own pair too. It signs with the private half when it calls Canvas services like AGS. Canvas reads the public half from /lti/jwks.

QuickPoll 1.3 makes the pair for each registration and stores both halves in lti_registrations. The private half sits unencrypted for now: that is a known gap.

What the tool checks

LTI 1.1 Four checks

Check 1
Known consumer
Find oauth_consumer_key in lti_consumers.
Check 2
Signature
Rebuild the base string, sign it with the secret, compare in constant time.
Check 3
Timestamp
Inside the allowed window.
Check 4
Nonce
Not seen before. Store it in used_nonces (unique index).

LTI 1.3 Checks, in this order

First: the login
State
Present, known, unused, under 10 minutes old.
Then: the token
Signature
Canvas public keys, RS256 only. A bad or odd token is refused before any claim is read.
Then: the claims
Who, for whom, when
iss is the platform. aud is our client id. exp is in the future. iat is not far ahead (60 seconds of slack).
Then: the meaning
Nonce, type, version, deployment
The nonce is the one we saved. The message is a resource link launch. The version is 1.3.0. The deployment belongs to this registration.
Last
Use up the state
One conditional update. A second launch with the same state fails.
The order matters. A failed check leaves the state unused, so a refused forgery cannot burn a real login. The state is marked used last, after every other check passes.

Install and setup

LTI 1.1 Paste XML, pick a secret

  1. The tool serves an XML cartridge at /lti/config.
  2. In Canvas: Settings, Apps, + App, Paste XML.
  3. You choose the consumer key and the shared secret. Type the same pair into the tool's database.

Canvas gives you nothing back. The tool needs no Canvas addresses, because Canvas contacts the tool and never the reverse.

LTI 1.3 Developer key, then a deployment

  1. The tool serves JSON at /lti/tool_config.
  2. In Canvas: Developer Keys, + Developer Key, LTI Key. Paste the JSON. Add the redirect URI. Turn the key on.
  3. Canvas gives you a client id, a long number like 10000000000011.
  4. Installing the key makes a deployment with its own id, like 21:<hash>. Set its availability to Available.
  5. Give the tool the Canvas addresses and both ids (rake lti:platform, rake lti:register).

The tool now calls Canvas too. It reads the Canvas keys, so it must know the Canvas JWKS address.

QuickPoll 1.1

  • lti_consumers: consumer_key, shared_secret, instance_guid
  • used_nonces: nonce, oauth_timestamp

QuickPoll 1.3

  • lti_platforms: issuer, auth_endpoint, token_endpoint, jwks_uri
  • lti_registrations: client_id, public_key, private_key, kid
  • lti_deployments: deployment_id
  • lti_launch_states: state, nonce, used_at

Identity: one person, two ids

Canvas gives the same person a different id in each version. The 1.3 launch carries both, so a tool can connect them.

LTI 1.3

A 36-character UUID. Stored in lti_users.lti1p3_sub.
The bridge
.../claim/lti1p1
Holds user_id, the old 1.1 value. Present in every live launch.
Checked live. The user_id inside the 1.3 claim matched lti1p1_user_id in the 1.1 database for the teacher, the TA, and the student. The claim held only user_id. It had no consumer key and no signature, because Canvas finds the old 1.1 tool by matching URLs, and the two apps use different hostnames. A cutover test would run the 1.3 app on the 1.1 address.

QuickPoll stores polls and votes against its own internal id (lti_users.id), not against either LTI id. That keeps votes attached to the person if the LTI id changes.

Browsers, iframes, and cookies

LTI 1.1

The launch is one POST that proves itself, so it needs no cookie. The tool starts a session after the check. That session cookie sits in an iframe, so it has the third-party cookie problem in production.

LTI 1.3

The login trip leaves the tool and comes back. The tool needs to remember state across that trip. A cookie would be the usual place, and an iframe may block it. QuickPoll 1.3 keeps the state in Postgres instead. That works anywhere, but nothing ties the state to this browser. After the launch it still uses a session cookie, with the same limit as 1.1.

The real fix is a platform storage handshake. The live 1.3 launch URL carried lti_storage_target=post_message_forwarding. That is Canvas offering a way to store state through browser messages. QuickPoll ignores it today.

Gotchas we hit going live

The client id is the long number. The short key id in the Canvas URL (11) is not the client id. The launch sends 10000000000011 as aud. A registration with the short value never matches.
A new install is unavailable. Canvas sets the deployment to unavailable. The link stays out of course navigation until you set Availability to Available.
Specs stub the network. The key download passed every spec and crashed in the first real launch, because net/http was not loaded. A live launch tests what a stub cannot.
A running server loads gems once. After a Gemfile change the running Puma lacked json-jwt. A restart fixed it.
