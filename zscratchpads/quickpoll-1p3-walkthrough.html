QuickPoll 1.3: How the App Works

A follow-along guide to an LTI 1.3 tool. It shows what Canvas and the tool each need, how they talk, what the tool checks, and which file does what.

The short version

🪪
One 1.3 launch is two browser trips and one signed token
Canvas tells the tool "someone clicked". The tool starts a login and saves a secret note (the state and nonce). Canvas sends a token that it signed. The tool checks the signature with the Canvas public keys, checks the claims, and lets the person in.
  • Canvas needs four things from the tool: a login URL, a launch URL, a place to find the tool's public key, and the placements (where the link shows).
  • The tool needs four things from Canvas: its name (the issuer), its addresses, the client id, and the deployment id.
  • No secret passes between them. Canvas signs with a private key. The tool checks with the matching public key.
  • The tool also makes its own key pair, and publishes the public half. Canvas reads it only when the tool calls a Canvas service, like grades. QuickPoll calls none yet.
It works live. A teacher, a TA, and a student each launched from the local Canvas. The teacher and the TA create polls. The student votes. 326 specs pass. The real roles and claim names in this page come from those launches (2026-11-14).

What Canvas needs, and what the tool needs

A 1.3 connection is two lists of values that each side must know about the other. Most failures come from one value that does not match.

Canvas needs from the tool

  • Login URL. Where Canvas sends the browser first. /lti/login.
  • Launch URL and redirect URI. Where the signed token gets posted. /lti/launch. Canvas checks the address against this list.
  • Public key address. /lti/jwks. Canvas needs it for service calls only.
  • Title, privacy level, placements. What the link says, which data Canvas sends, and where the link shows.
  • Scopes. The services the tool may call. QuickPoll lists none.

The tool needs from Canvas

  • Issuer. Canvas's name inside every token (iss).
  • Auth endpoint. Where the tool sends the browser in trip 1.
  • JWKS address. Where the tool downloads the Canvas public keys.
  • Client id. Which developer key the launch belongs to (aud).
  • Deployment id. Which install the launch came from.
  • Token endpoint. Needed for service calls only. Stored, not used yet.

Where each value comes from

Value Made by Where you see it Where it lives in QuickPoll
Login URL Tool App page: "Open ID Connect Initiation URI" /lti/login, JSON oidc_initiation_url
Launch URL Tool App page: "Redirect URIs" and "Default Target Link URI" /lti/launch, JSON redirect_uris and target_link_uri
Tool public key address Tool App page: "Public JWK URL" /lti/jwks, JSON public_jwk_url
Issuer Canvas Fixed for this Canvas: https://canvas.instructure.com (lti_iss in Canvas's security.yml) lti_platforms.issuer

Canvas JWKS Canvas Canvas source: /api/lti/security/jwks lti_platforms.jwks_uri
Token endpoint Canvas Canvas source: /login/oauth2/token lti_platforms.token_endpoint

rake lti:platform fills in the four Canvas addresses. rake lti:register CLIENT_ID=... DEPLOYMENT_ID=... adds the registration (and makes its key pair) and the deployment.

The JSON Canvas reads

Canvas fetches this from /lti/tool_config (or you paste it in) when you make the developer key. Each field answers a question Canvas has.

{
  "title": "QuickPoll 1.3",                         # the name in the app list
  "description": "QuickPoll 1.3 LTI Tool",          # Canvas requires one
  "oidc_initiation_url": ".../lti/login",           # trip 1 goes here
  "target_link_uri": ".../lti/launch",              # default launch address
  "redirect_uris": [".../lti/launch"],              # Canvas posts the token only here
  "public_jwk_url": ".../lti/jwks",                 # the tool public keys
  "scopes": [],                                     # no services requested
  "extensions": [{
    "platform": "canvas.instructure.com",
    "privacy_level": "public",                      # names and email may be sent
    "settings": { "placements": [{
      "placement": "course_navigation",             # the link lives in the course menu
      "message_type": "LtiResourceLinkRequest",
      "text": "QuickPoll 1.3",
      "target_link_uri": ".../lti/launch"
    }]}
  }]
}
The app page proves it worked. Canvas filled "Redirect URIs", "Default Target Link URI", "OpenID Connect Initiation URI", and "Public JWK URL" from this JSON. The Developer Keys list did not show the key (a mystery: the Apps page lists it).
A new tool is not available yet. Canvas installs it unavailable. Set it to Available under "Availability and Exceptions", or the link never shows.

Trip 1: the login (Lti::LoginController)

Canvas calls /lti/login with four values the tool reads: iss, client_id, login_hint, and lti_message_hint (optional). Canvas may send more. The tool ignores them.

1
Find who is asking
Look up the platform by iss, then the registration by client_id. No match, or a blank login_hint: answer 400.
2
Make a note
Make a random state and nonce. Save both in lti_launch_states, tied to the registration.
3
Send the browser to Canvas
Redirect to the platform's auth endpoint with the parameters below.
Parameter Value Why
scope openid OpenID Connect requires it.
response_type id_token Canvas answers with a token, not a code.
response_mode form_post Canvas posts the token to the tool in a form. The token never rides in a URL.
prompt none No login screen. The person is already signed in to Canvas.
client_id the registration's id Tells Canvas which developer key.
redirect_uri .../lti/launch Where Canvas posts the token. Canvas checks it against the registered list.
login_hint copied from Canvas Canvas uses it to find who is logging in.
lti_message_hint copied from Canvas, when sent Canvas uses it to find which link was clicked.
state random, saved Canvas returns it unchanged. It ties the answer to this login.
nonce random, saved Canvas puts it inside the signed token. It stops a replayed token. 
# app/controllers/lti/login_controller.rb (trimmed)
platform     = LtiPlatform.find_by(issuer: params[:iss])
registration = platform&.lti_registrations&.find_by(client_id: params[:client_id])
return head :bad_request if registration.nil? || params[:login_hint].blank?

state = SecureRandom.hex(16)
nonce = SecureRandom.hex(16)
registration.lti_launch_states.create!(state: state, nonce: nonce)
redirect_to "#{platform.auth_endpoint}?#{query.to_query}", allow_other_host: true
The state lives in Postgres, not in a cookie. The tool runs in an iframe, and browsers block third-party cookies in iframes. A database row works anywhere. The price: nothing ties the state to this browser. Anyone who learns an unused state could try to finish that launch, but they would also need a valid token signed by Canvas that holds the saved nonce. The fix for later is Canvas's storage handshake (lti_storage_target, which the launch URL already carries).

Trip 2: the token (Lti1p3::LaunchVerifier)

Canvas posts id_token and state to /lti/launch. The verifier runs these checks in this order, and the first failure stops it. It records one error symbol. The controller answers 401 with the words "Launch rejected." and logs [lti launch] rejected: <symbol>. The page never says why. The log does.

# Check Error symbol What it stops
1 state is present missing_state A post that skipped the login.
2 id_token is present missing_id_token An empty post.
3 The state exists unknown_state A made-up state.
4 The state is unused state_used A replay of a finished launch.
5 The state is under 10 minutes old state_expired A login someone left open.
6 The Canvas keys download keys_unavailable Canvas down, or an answer that is not JSON. The tool refuses rather than guess.
7 The token is a JWT malformed_token Garbage in the field.
8 The signature matches a Canvas key bad_signature A forged token, the wrong key, an alg: none token, an HS256 trick. The code allows RS256 only.
9 exp, iat, sub, and the course id exist missing_claim A token the tool cannot use.
10 iss is this platform wrong_issuer A token from another platform.
11 aud is this client id wrong_audience A token meant for a different tool. aud can be a string or an array.
12 exp is in the future expired An old token.
13 iat is not over 60 seconds ahead issued_in_future A token from a clock far ahead of ours. 60 seconds of slack covers small clock drift.
14 nonce equals the saved one wrong_nonce A token for a different login.
15 The message is LtiResourceLinkRequest unsupported_message_type A deep linking request, which the tool does not handle.
16 The version is 1.3.0 unsupported_version Another LTI version.
17 The deployment id belongs to this registration unknown_deployment An install the tool does not know.
18 Mark the state used (a late loser gets state_used) Two requests with the same state at once. One conditional update picks one winner.
A failed check leaves the state unused. A forged post cannot burn a real login. The state is used up last, only after everything else passes. The tool never logs the token (a spec checks it).

What the token holds

These are the real claim names from a Canvas launch, grouped by what QuickPoll does with them. Values are not shown, because they hold names and ids.

The tool uses

issaudsubexpiatnoncename

Plus these full-URL claims (each starts with https://purl.imsglobal.org/spec/lti/claim/): message_type, version, deployment_id, roles, context.

The tool sees and ignores

azppicturegiven_namefamily_nameemaillocale

And these claim URLs: resource_link, target_link_uri, lis, tool_platform, launch_presentation, custom, eulaservice, lti11_legacy_user_id, lti1p1, and Canvas's own https://www.instructure.com/placement.

Private data. name, picture, and email are personal data (FERPA, and GDPR for EU users). email showed up for the TA only. The tool saves sub and name. It saves no email. Keep real launches out of docs and logs.

After the check passes

Step 1
Find or make the person and the course
Lti1p3::LaunchRecords looks up the person by sub and the course by the context id, both through the platform. The same sub on another platform is another person. A blank name or title keeps the old one. One transaction.
Step 2
Start a clean session
reset_session first (this stops session fixation). Then store the person id, the course id, and a yes or no: can_create_polls.
Step 3
Redirect
A 303 to /lti/polls. The 303 tells the browser to load the next page with a GET.

Roles, as Canvas really sends them

Person Roles claim (real) Names Create polls?
Teacher institution/person#Instructor, membership#Instructor, system/person#User Instructor, User Yes
Student institution/person#Student, membership#Learner, system/person#User Student, Learner, User No
TA institution/person#Instructor, membership#Instructor, membership/Instructor#TeachingAssistant, system/person#User Instructor, TeachingAssistant, User Yes

Each URI starts with http://purl.imsglobal.org/vocab/lis/v2/. The name is the text after the last #. With no # it is the text after the last /. A TA also carries membership#Instructor, so a TA reads as an instructor too.

The database

Expand and contract. lti_users and lti_contexts got a nullable lti_platform_id. The old consumer column became nullable. A row needs a consumer or a platform. That let the 1.1 and 1.3 launches share the same tables while both existed.
Unique keys do the safety work. One sub per platform. One context_id per platform. One state everywhere. One vote per person per poll.

The two key pairs

The Canvas pair Canvas

🔐Private half: stays in Canvas. It signs every id_token.
🔓Public half: Canvas serves it at /api/lti/security/jwks. The tool downloads it on every launch (step 8 of the picture).

The token header names the key (kid). The verifier tries the downloaded set. A new key from Canvas needs no change in the tool.

The tool pair QuickPoll

🔐Private half: lti_registrations.private_key. Made with RSA 2048 when the registration is made. Plain text today.
🔓Public half: /lti/jwks serves the public key of every registration.

Nothing uses this pair yet. It exists for service calls: the tool would sign a request for a Canvas access token with it. That is the first step of grade passback (AGS).

Easy to miss

The connection is a triple. One tool can face many platforms. The launch names the platform (iss), the developer key (aud), and the install (deployment_id). The tool checks all three. A deployment_id is only valid under its own registration.
Redirect URIs must match. Canvas posts the token only to an address in the registered list. Copy the address character for character. I did not test which near-matches Canvas accepts. Production needs HTTPS. Only local development uses plain HTTP.
Specs cannot see the network. They stub the key download. Two real bugs only showed in the first live launch. Always do one live launch.
The cookie question is open. The launch works because state is in Postgres. The session cookie after the launch works locally because Canvas and the tool share a parent domain. In production an iframe may block it. It needs SameSite=None; Secure, and Safari may still block it.
The tool trusts the signature, not the network. Plain HTTP between the tool and Canvas would let someone swap the key download. Use HTTPS to fetch the keys in production. Cache them by kid and add a timeout. Today there is neither.
The private key is plain text. Encrypt it (Rails encrypts) or move it to a secrets store before real use.
Privacy level controls what you get. public sends names and email. Other levels send less. Change it in the JSON, then update the key in Canvas.
Placements are one line. Only course_navigation is set. Canvas has many others (account navigation, assignment selection, editor button). Each is another entry in the JSON. Some need Deep Linking.
Message types. The tool handles LtiResourceLinkRequest only. A deep linking request is refused on purpose.
Two votes at once. A simultaneous double vote can raise a database error (500). The unique index keeps the data right. The page does not catch the error yet.
Services are a second project. Grades (AGS), roster (NRPS), and content picking (Deep Linking) need scopes in the JSON, a token request signed with the tool's key, and more specs. The dynamic registration standard can replace the manual setup entirely.
Governance. Launch data (names, sub, sometimes email) is student and teacher data: FERPA, and GDPR for EU users. Use synthetic users in demos. Get Security and Privacy review before any real account installs the tool.

When it breaks

What you see Likely cause What to do
QuickPoll 1.3 is missing from the course menu The deployment is unavailable. App page, Availability and Exceptions, set to Available.
Login answers 400 Unknown issuer or client id, or a blank login_hint. Run rake lti:platform and rake lti:register. Use the long client id.
Canvas shows an error at the authorize step The redirect URI is not in the developer key. Add .../lti/launch to Redirect URIs.
Log: rejected: wrong_audience The registered client id is not the one Canvas sends. Re-register with the "Copy Client ID" number.
Log: rejected: unknown_deployment The deployment id is not registered. Add it with rake lti:register.
Log: rejected: keys_unavailable The tool cannot reach the Canvas JWKS. From the tool container, curl the JWKS address.
Log: rejected: state_used or state_expired A refresh or a back button. Click the link in Canvas again. Each click starts a new login.
A page of Ruby error text with NameError A gem or file the running server has not loaded. docker compose restart web.

Read the reason from any directory: docker logs quickpoll_1p3-web-1 --tail 100 2>&1 | grep "\[lti launch\]"

Vocabulary

platform
The LMS (Canvas). Also called the issuer. One platform row per LMS.
tool
The app Canvas launches. QuickPoll.
issuer (iss)
The platform's name inside a token. Here, https://canvas.instructure.com.
client_id (aud)
The developer key. It names the tool to Canvas. In the token it is the audience: who the token is for.
deployment_id
One install of the tool in an account or course. Many deployments can share one client id.
registration
The tool's row for one client id: its key pair and its deployments.
OIDC login
The two-step login (OpenID Connect) the 1.3 launch rides on.
login_hint
Canvas's private note about who is logging in. The tool hands it back untouched.
state
A random value the tool makes in trip 1. Canvas returns it. It ties the answer to the login.
nonce
A random value the tool makes in trip 1. Canvas puts it inside the signed token. It stops replays.
JWT / id_token
A signed JSON message in three parts: header, payload (the claims), signature.
JWKS
A web address that lists public keys as JSON. Each key has a kid.
kid
Key id. The token header names which key signed it.
claim
One fact inside the token payload, like name or the roles list.
placement
Where in Canvas the link lives. Here: course navigation.
scope
Permission to call a Canvas service. QuickPoll asks for none.
sub
Subject: the person's id in the token. Unique inside one platform.
